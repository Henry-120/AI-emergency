# 藍牙 SOS 多跳中繼網路 — 設計文件

日期：2026-07-13
負責模組：藍牙（BLE）
狀態：設計已確認，待撰寫實作計畫

---

## 1. 背景與目標

GuardiaAI 的核心情境是「斷網、停電的災害當下」。目前藍牙模組（`src/services/bluetooth/`）已能做到：iOS 原生 peripheral 廣播、Central 掃描、點對點單向傳訊。但它只能在「兩支手機互相看得見」時運作——受困者若身邊沒有人，訊息就出不去。

本設計要解決的問題：**受困者沒有網路訊號時，如何讓求救訊息傳到外界。**

做法是把附近的手機變成接力節點。求救封包在裝置之間多跳擴散，直到碰到一支有網路的手機，由它代為上傳後端報案。這在學術上屬於 delay-tolerant network（DTN）／epidemic routing，有充足的 IEEE 文獻可引用，對應工作分配表第一項「尋找論文報告（未來可擴展的功能）」。

### 成功標準

1. 三支實機演練：A（飛航模式）發出求救 → B 中繼 → C（有網路）自動上傳後端 → ACK 回傳到 A，A 的畫面顯示「求救已送出」。
2. 中繼者全程無法讀取求救內容（位置、身分、醫療資訊）。
3. 介面上不出現任何藍牙術語，沒有相關知識的使用者也看得懂。

## 2. 信任模型（本設計的核心原則）

**中繼者是陌生人，不在信任範圍內。**

中繼者只負責搬運，不得開箱。他能讀到的僅限路由所需的明文標頭，以及一個粗略的嚴重程度旗標；精確位置、身分、醫療摘要、求救文字全部加密，只有後端解得開。

這條原則推導出兩個必要的安全設計：

- 內容加密：中繼者讀不到求救內容。
- ACK 簽章：中繼者偽造不出「已送達」回執。若可偽造，惡意節點就能讓受困者誤以為求救成功而停止呼救——這比洩漏內容更危險。

---

## 3. 訊息協定

所有在網路中流動的訊息共用同一種封包，以 `type` 區分用途。新增訊息類型不需修改中繼邏輯。

| type | 用途 | 方向 |
|------|------|------|
| `SOS` | 求救 | 受困者 → 外界 |
| `ALERT` | 轉播中央氣象署警報給沒訊號的人 | 有網路者 → 外界 |
| `ACK` | 求救已成功上傳的回執 | 後端 → 受困者 |

### 3.1 明文標頭（中繼者讀得到）

| 欄位 | 大小 | 說明 |
|------|------|------|
| `ver` | 1 byte | 協定版本 |
| `keyVersion` | 1 byte | 後端金鑰版本。後端輪替金鑰後，舊版 App 的封包仍能被正確解讀 |
| `type` | 1 byte | `SOS` / `ALERT` / `ACK` |
| `msgId` | 8 bytes | 訊息唯一識別，用於去重 |
| `ttl` | 1 byte | 剩餘跳數，初始 4，每轉發一次減 1，歸零不再轉發 |
| `hops` | 1 byte | 已跳躍次數，用於 UI 顯示「已傳到 N 跳之外」 |
| `severity` | 1 byte | 粗略嚴重程度旗標（bitfield：受困 / 受傷）。**不含身分與位置** |

`ttl` 與 `msgId` 去重是防止訊息在裝置間無限彈跳、耗盡電池的兩個控制手段，缺一不可。

### 3.2 加密內容（只有後端讀得到）

密文中包含：精確 GPS 座標、發送者 localId、求救文字（可由語音輸入產生）、醫療摘要（血型、藥物過敏、慢性病，取自 `medicalCardService`）、裝置電量、時間戳記。

### 3.3 加密設計

採用標準混合加密（hybrid encryption）：

1. App 內建後端公鑰（必須內建——災難當下無網路可取得金鑰）。
2. 發送時產生臨時金鑰對，與後端公鑰做 ECDH（P-256）導出對稱金鑰。
3. 以 AES-256-GCM 加密內容；GCM 同時提供完整性驗證。
4. 封包附上臨時公鑰、IV、認證標籤。
5. 後端以私鑰解密。

使用 Web Crypto API（`crypto.subtle`），iOS WebView 原生支援 ECDH P-256 與 AES-GCM，不需外部密碼學函式庫。

**成本（實作後修正）**：

| 項目 | bytes |
|------|-------|
| 臨時公鑰 | 65 |
| IV | 12 |
| GCM 認證標籤 | 16 |
| **加密開銷小計** | **93** |
| 明文標頭 | 14 |

原先估計為 61 bytes，係假設可用壓縮點（33 bytes）。實作時發現 SubtleCrypto 的 `exportKey("raw")` 只輸出**未壓縮點**（65 bytes），壓縮點需自行實作橢圓曲線點解壓縮（模平方根），不值得為 32 bytes 增加這個複雜度與出錯風險。

因此實際開銷為 93 + 14 = 107 bytes，加上求救內容本身，加密後的封包必然超過單一 BLE 封包的容量。**分片機制因此是必要前置，而非最佳化選項**——此點已在 `bluetoothChunking.ts` 完成並有測試覆蓋。

### 3.4 ACK 防偽

ACK 與其他封包一樣有自己的 `msgId`（供中繼者去重）與 `ttl`（供回程擴散）。其內容為：

```
{ refId: <原 SOS 的 msgId>, uploadedAt: <後端收件時間> }
```

此內容由後端以私鑰簽章（ECDSA P-256）。受困者的 App 以內建公鑰驗簽，並比對 `refId` 是否為自己發出的求救；驗簽失敗或 `refId` 不符即丟棄。

`refId` 為明文——中繼者本來就看過該 SOS 的 `msgId`，不構成新的資訊洩漏，但可讓中繼者順帶清理待轉發佇列中已送達的封包。

中繼者可搬運 ACK，但因無後端私鑰而無法偽造。這是必要的：若 ACK 可偽造，惡意節點就能讓受困者誤信求救已送出而停止呼救。

## 4. 中繼演算法

```
收到封包：
  1. 驗證明文標頭格式，格式錯誤 → 丟棄
  2. msgId 已在 seenIds 中 → 丟棄（去重）
  3. 記入 seenIds（LRU，上限 200 筆）

  4. 若 type = ACK：
       驗簽失敗 → 丟棄
       refId 是我發出的求救 → 顯示「求救已送出」，不再轉發
       否則 → 從待轉發佇列移除 refId 對應的封包，續行第 6 步（幫忙把 ACK 傳回去）

  5. 若 type = SOS/ALERT 且我有網路：
       將密文原封不動上傳後端（不解密，也解不開）
       上傳成功 → 不再轉發（訊息已離開藍牙網路）
       上傳失敗 → 續行第 6 步，改走中繼路徑

  6. 轉發判斷：
       ttl == 0        → 不轉發
       電量 < 20%      → 不轉發（保命優先，只接收）
       否則            → ttl -= 1, hops += 1，存入待轉發佇列

  7. 週期性掃描時，將待轉發佇列的封包送給掃到的每個 GuardiaAI 節點
```

### 電量感知的中繼選擇

`EmergencyStatus` 已有 `batteryLevel`。以電量分三段決定本機承擔多少中繼工作：

| 電量 | 行為 |
|------|------|
| < 20% | 只接收，不轉發。保住自己的求救能力優先 |
| 20–50% | 正常轉發，但掃描週期拉長為每 30 秒掃 5 秒以省電 |
| > 50% | 全速轉發，掃描週期每 15 秒掃 5 秒 |

學術上稱為 energy-aware relay selection，可引文獻；實作上只是依電量選擇掃描間隔與是否轉發。

## 5. 架構（新增檔案）

維持現有分層原則：UI 只 import facade（`bluetoothService.ts`），不直接碰底層。

| 檔案 | 職責 |
|------|------|
| `src/services/bluetooth/sosProtocol.ts` | 封包格式、序列化／反序列化、`msgId` 生成 |
| `src/services/bluetooth/sosCrypto.ts` | 混合加密、ACK 驗簽、內建公鑰管理 |
| `src/services/bluetooth/relayStore.ts` | store-and-forward：`seenIds` 去重表（LRU 200）、待轉發佇列 |
| `src/services/bluetooth/relayEngine.ts` | 中繼引擎：常駐掃描、轉發決策、TTL／電量判斷 |
| `src/services/bluetooth/uplinkBridge.ts` | 有網路時把密文推向後端；沿用既有 `offlineQueueService` |

`relayEngine` 獨立成引擎而不塞進 `bluetoothService`，因為它有自己的生命週期（常駐掃描迴圈）與狀態機，混進 facade 會讓後者變成什麼都做的大檔案。

## 6. 技術前置（不做這三件事，上面全部無法運作）

### 6.1 撐開 MTU（必要）

`bluetoothConstants.ts` 目前的 `MAX_MESSAGE_BYTES = 180` 是自行設定的保守值，註解引用的「GATT 預設 MTU 約 23 bytes」是 BLE 4.0 的舊數字。iPhone 對 iPhone 使用 write-with-response 時，ATT MTU 通常可協商到 185 甚至 512 bytes。

必須實測 iOS 的 `maximumWriteValueLength`，據以提高上限；超出長度時做分片（chunking）。加密後的求救封包（內容 + 61 bytes 加密開銷 + 14 bytes 標頭）在 180 bytes 的限制下塞不下。

### 6.2 掃描改為常駐（必要）

目前 `scanNearby()` 是 one-shot：掃 8 秒、回傳快照。中繼者必須持續在線才接得到訊息，需改為週期性掃描迴圈；掃描間隔依電量調整，見第 4 節的電量分段表。此改動同時解決 `getStatus()` 中寫死的 `isScanning: false`。

### 6.3 背景身分識別（已知限制，暫不硬拚）

iOS App 進入背景後，系統會從廣播封包中剝除 LocalName——對方掃得到你，但認不出你是 GuardiaAI 使用者。

**本階段的決定：先做前景中繼**（demo 時三支手機都開著 App），並將背景限制誠實寫入報告的「限制與未來工作」章節。強行對抗 iOS 背景廣播限制的投資報酬率過低。

## 8. UI 與文案原則

工作分配表明確要求：「搞清楚初始化、廣播那些是什麼意思並改寫讓沒這方面知識的使用者也看得懂」。

**規則：介面上不得出現任何藍牙術語。** 禁用「初始化」「廣播」「掃描」「Peripheral」「Central」「RSSI」「GATT」。

| 技術概念 | 介面文案 |
|----------|----------|
| 開始廣播 | 讓附近的人看見我 |
| 掃描附近裝置 | 尋找附近的人 |
| RSSI 數值 | 很近 / 附近 / 較遠（不顯示 dBm） |

求救頁面的主體是一顆大按鈕「發出求救」（符合 PRODUCT.md 的「大觸控目標、拇指熱區」）。按下後的狀態依序為：

1. 「求救已發出，正在尋找附近的人幫忙轉傳…」
2. 「已有 2 人收到你的求救」
3. 「你的求救已成功送出報案」

第 3 步（ACK 送達）在技術上只是第三種封包類型，但它是整個功能中對使用者心理最關鍵的一環——PRODUCT.md 的產品目標是「穩住使用者」，讓求救者確知訊息真的送出去了，正是這件事。

## 9. 驗證計畫

BLE 無法在模擬器上執行，也無法以單元測試證明端到端行為。驗證分兩層：

**協定邏輯（可自動化測試）**：將去重、TTL 遞減、電量門檻、封包序列化／反序列化、加密解密、ACK 驗簽寫成純函式，以單元測試覆蓋。不需實機。

**多跳中繼（必須實機演練）**：三支 iOS 實機。
1. A 開飛航模式（僅開藍牙），發出求救。
2. B 在 A 的藍牙範圍內、無網路，接收並中繼。
3. C 在 B 的範圍內、有網路，自動上傳後端。
4. 後端簽章 ACK，經 C → B → A 回傳。
5. 驗證 A 的畫面顯示「求救已送出」，且 B、C 的裝置上無法看到 A 的位置與醫療資訊。

此演練腳本可直接作為論文的實驗章節。

## 10. 已知限制

1. **背景中繼受限**：iOS 背景時廣播的 LocalName 被系統剝除，「手機放口袋自動中繼」的真實情境無法完整達成。本階段僅支援前景中繼。
2. **Android 無法廣播**：peripheral 為 iOS 原生實作（`canAdvertise()` 限定 iOS）。Android 端僅能掃描與接收，無法發出求救。
3. **RSSI 不可作為精確距離**：雜訊大，僅能表達遠近趨勢。
4. **惡意節點可丟棄或洗版封包**：加密可防竊聽與偽造，但無法防止中繼者拒絕轉發（black hole attack）或大量灌送垃圾封包。偽造的封包會在後端解密失敗而被丟棄，無法注入假求救。

## 11. 未來展望（論文可寫、本階段不做）

- **離線 LLM 的運算卸載**：電量低或未下載模型的裝置，透過 BLE 將問題送給鄰近有離線 LLM 的裝置代為推論（computation offloading）。
- **AR 訊號尋人**：以 RSSI 強弱做熱／冷導引，在 AR 畫面疊出受困者的大致方向。視覺效果強，但 RSSI 雜訊使其只能做趨勢引導，不能做精確定位。
- **背景常駐中繼**：改以 service data 或 GATT read 承載身分，對抗 iOS 背景廣播限制。
- **更聰明的路由**：目前是 epidemic routing（見人就傳）。可評估 Spray-and-Wait 等策略以降低網路負載。
