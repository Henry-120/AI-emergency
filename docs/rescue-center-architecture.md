# 救援端工作台：概念與架構草案

**狀態：** 討論稿，供後續實作與試辦需求確認使用  
**產品定位：** 災情資訊協作與救援任務輔助，不取代 119、官方災害應變中心或既有指揮系統。

## 1. 產品方向

救援端先以「災情協調／指揮中心工作台」為主。民眾提供現場回報，AI 協助整理與找出相似資訊，協調人員核實、排序並派遣任務；外勤人員之後使用較精簡的行動介面接收所屬任務、回報進度。

目前原型已有協調員建立隊伍、以隊伍邀請碼加入外勤帳號、任務派遣與外勤進度回報的基本流程；尚未具備組織隔離、隊伍管理員、邀請碼撤銷／輪替及正式營運所需的完整權限治理。後續應以輔助既有應變流程為原則。消防署對 EMIC 的說明已涵蓋依權限與服務類型進行災情通報、查報及任務指派，因此本專題應優先驗證「民眾第一手資訊彙整、跨來源案件連結、AI 摘要與離線回報」等差異能力，再評估與既有系統的合作或資料交換方式。[消防署 EMIC 介紹](https://www.nfa.gov.tw/cht/index.php?act=article&article_id=10361&code=print&ids=1537)

## 2. 使用角色與責任

| 角色 | 主要任務 | 權限原則 |
|---|---|---|
| 平台管理者 | 維護服務、建立機關租戶、處理平台層級設定 | 不應預設瀏覽日常案件內容；必要存取需留稽核紀錄 |
| 機關管理者 | 邀請／停用成員、設定所屬區域與隊伍、分派機關角色 | 僅管理自己的組織 |
| 災情協調員／調度員 | 核實回報、連結或拆分案件、調整優先級、指派隊伍、追蹤全域進度 | 可操作所屬機關獲授權的事件與服務區域 |
| 外勤救援人員 | 查看派給自己的任務、回報出發／抵達／處理結果及現場資訊 | 預設只能讀取自己或所屬隊伍的任務；不能任意結案他隊案件 |
| 觀察／合作單位 | 查看明確授權的災情摘要或任務進度 | 唯讀、最少必要資料，不顯示不必要的醫療或身分資訊 |

目前可先實作「機關管理者、災情協調員、外勤救援人員」三種角色；觀察者及平台管理者可在試辦需要時補上。不同機關的職稱和實際權責需由合作單位確認，不能只依軟體預設推定。

## 3. 核心工作流程

```text
第一手回報／SOS
        ↓
回報收件與地理定位
        ↓
協調員核實、找相似回報、建立或連結救援案件
        ↓
依透明規則排序並指派隊伍
        ↓
外勤隊伍接受任務、出發、抵達、回報處置
        ↓
協調員確認結果並結案
```

### 回報狀態與救援案件狀態要分開

- 回報、受災者案件和隊伍任務各有自己的生命週期；詳細狀態與自動轉換規則見「決策 002」。

「收到一筆回報」不等於「建立一個獨立救援案件」；「某隊完成任務」也不必然代表整個災情案件已結案。系統應保留這些不同狀態，避免把回報流程和救援進度混成同一個欄位。

### 決策 002：以三組狀態管理回報、個案與隊伍任務

**決策日期：2026-10-28**  
**性質：** 本專題 MVP 的建議流程；真正試辦前須由合作單位核對其 SOP、職權與用語。

| 對象 | 狀態流程 | 更新權責 |
|---|---|---|
| 現場回報 | `已收到` → `待核實` → `已核實`／`疑似重複`／`不採用` | 系統建立回報並放入佇列；協調員確認真偽與重複關係。相似度只能產生建議，不能自動合併或刪除原文 |
| 受災者案件 | `待核實` → `已確認需要救援` → `待派遣` → `已派遣` → `救援中` → `待確認結果` → `已協助` → `結案` | 協調員負責確認個人案件、需要救援與結案；派遣及任務進度可依下表同步更新 |
| 救援任務 | `待接受` → `已接受` → `前往現場` → `已抵達` → `任務完成`；另有 `拒絕／取消／改派` 分支 | 協調員建立、改派或取消任務；外勤隊伍回報接受、行程和現場處置結果 |

#### 哪些轉換可以自動發生？

**可以自動化的是確定的流程同步，不是對現場事實作猜測。**建議區分「來源狀態」、「人員確認狀態」和「由任務推導的案件顯示狀態」。

1. **新資料進來：可以自動。**收到一筆現場回報或 SOS 後，系統建立來源紀錄並放入「待分流／待核實」佇列；這只表示系統收到資料，不代表內容已證實。一般災情回報先建立分流項目，不自動宣稱一個人受災；協調員判斷回報是否指向獨立受災者後，才建立 `待核實` 的受災者案件。
2. **派遣任務後：可以同步案件狀態。**協調員成功建立並指派任務後，對應案件可自動變成 `已派遣`；任務狀態進入 `前往現場` 或 `已抵達` 後，案件可顯示 `救援中`。這類轉換應記錄觸發它的任務和操作者。
3. **所有相關任務完成後：可以轉為待確認，不能直接結案。**若案件連結的任務都已完成，且隊伍有提交處置結果，系統可將案件改為 `待確認結果`，提醒協調員檢查結果。
4. **任務完成不等於受災者已獲協助。**任務可能是搜索、送物資、初步評估或支援其他隊伍；即使隊伍按下「任務完成」，仍要看提交的結果和案件是否還有未完成需求。協調員確認結果後才將案件標為 `已協助`，再完成紀錄和必要覆核後 `結案`。
5. **不可自動核實、合併或結案。**系統不能僅依 AI 摘要、文字相似度、GPS 靠近或任務完成，就認定回報為真、兩筆資料屬於同一人，或受災者已安全。
6. **允許重開，但必須留理由。**若新回報顯示已結案者仍有需求，授權協調員可以重開案件或開新任務；系統保留前一個結案紀錄及重開原因。

當回報只說「某處多人受困／受傷」但人數或個人身分不明時，先保留為現場分流項目，必要時派「搜索此現場」任務；待現場人員查明後再建立一筆個人案件。這樣既可以讓救援行動先開始，也不會把未知人數誤當成已確認的個案數。

案件若有多筆任務，`救援中` 應表示至少有一筆有效任務正在執行；只有當所有相關任務都有結果，才進入 `待確認結果`。若所有任務被拒絕或取消，案件應回到 `待派遣`，不能留在看似有人處理的狀態。

每次人工或自動狀態變更都應新增一筆不可覆寫的操作歷程，至少包括操作者（或系統觸發器）、時間、物件、前後狀態、理由／處置結果和關聯任務。消防署對 EMIC 的介紹也描述依帳號權限和服務類型處理災情與任務；FEMA 的事故管理教材則要求資源狀態變更由負責人員通知並更新。這些可作為流程設計參考，但本表不是台灣各單位的正式 SOP，試辦時仍需合作單位確認。[消防署 EMIC](https://www.nfa.gov.tw/cht/index.php?act=article&article_id=10361&code=print&ids=1537)、[FEMA NIMS 資源狀態參考](https://www.fema.gov/pdf/emergency/nrf/nrf-nims.pdf)

### 去重與 AI 排序

- 原始回報應保留，不因去重而刪除；相似回報可連結至同一案件，並標記為疑似重複或已合併。
- 以地震事件、時間、距離、文字相似度及來源等訊號提出「可能相關」建議；由協調員確認是否合併。
- AI 摘要須連回來源回報並說明不確定性；AI 可協助整理，不可自行把未核實觀察標為事實或自動結案。
- 優先級應以可解釋規則為主，例如受困、立即生命危險、傷勢、等待時間與位置可用性；AI 可提供建議，最終處置由有權責的人員確認。

### 情境演練：檢查流程與案件定義

| 情境 | 系統與協調員應如何處理 | 要驗證的邊界 |
|---|---|---|
| 同一場地震有三位民眾各自回報 | 三份原始回報使用同一 `DisasterEvent`；各自進入分流。若分別描述三名受災者，建立三個 `RescueCase`；AI 災情摘要可彙整三份回報，但不把三人合成一案 | 同事件分組與個人案件是不同層次；事件 key 必須一致 |
| 同一人有一般救援摘要、兩筆 SOS，旁人也回報他 | 系統先保留四筆來源；協調員核對後，把它們連到同一個 `RescueCase`，來源資料不刪除。若身分仍不明，先保持分開或標成待核實 | 不以同地點、相似文字或多個訊息 ID 自動認定同一人 |
| 一筆回報稱「某建物多人受困」，人數未明 | 建立現場分流項目並可派現場搜索任務；隊伍回報人數和結果後，再逐人建立個人案件 | 不因一句「多人」就自動生成任意數量的個人案件；搜索任務完成也不等於人員獲救 |
| 同一位受災者需要兩支隊伍分別處理 | 兩筆任務連到同一個 `RescueCase`。第一隊完成時案件仍保持處理中；所有任務都回報結果後，案件轉 `待確認結果`；協調員核對後才確認協助與結案 | 單一任務完成不能自動結案；多任務都要有可追溯結果 |

## 4. 建議資料模型

### 決策 001：救援案件以「一名需要救援的人」為單位

**決策日期：2026-10-28**

指揮中心工作台中的標準 `RescueCase` 定義為**一名已知或匿名、需要被確認／協助／救援的受災者**。案件不是整場地震，也不是一個地點。

- **DisasterEvent（災害事件）**代表一次地震、火災等災害。例：某次 CWA 地震事件。
- **RescueSite（現場地點）**代表一個實際位置或搜救範圍。例：一棟倒塌建物、某路口或一處淹水區；現場可有危害資訊和待確認人數。
- **RescueCase（受災者案件）**代表一名需要處理的個人。可先匿名或身分未知，之後再補資料；每人各自有傷勢、需求、核實狀態和救援結果。
- **Mission（救援任務）**代表派給某支隊伍的一項工作，可針對一名受災者，也可先派「搜索某現場」任務，尚未確認個人案件時不虛構受災者數量。
- **FieldReport（現場回報）**和 SOS 是資訊來源紀錄；它們可以連結到一個現場、一名受災者案件，或暫時維持待分流狀態。原始回報應保留，不因合併而刪除。

基本關係：一個災害事件可包含多個現場；一個現場可關聯多名受災者案件及多筆現場回報；一名受災者可有多筆回報和多次任務紀錄。位置是案件的重要屬性，但不能把「同地點」當成「同一個人」。

**未能辨識人數時的處理：**若回報說「建物內有人受困」或「多人受傷」但沒有足夠資訊辨認個人，先建立現場／待核實的搜救項目，保存原始描述與「至少／約／未知」的人數線索；不要直接建立多筆個人案件。協調員確認有幾名獨立受災者後，再建立各自案件並連結來源。

### 為什麼要現在定義：既有資料是有做，但還不是同一種「案件」

專題已經有地震回報、一般使用者救援摘要、藍牙 SOS 和救援地圖，也有一些狀態欄位；所以你記得「原本已經做好」是對的。尚未完成的是：**這些不同來源的每一筆紀錄，究竟代表一個人、一個現場觀察，還是一次求救訊息？**目前沒有一個共同的 `RescueCase`，把它們連到同一名受災者或同一個現場。

| 目前資料 | 現在一筆資料代表什麼 | 為何不能直接視為標準救援案件 |
|---|---|---|
| `emergency_reports` | 以 `user_id` 為文件 ID 的該使用者目前救援摘要、位置與需求 | 接近「每位登入使用者的一份目前狀況」，更新時會覆寫同一份文件；不是每次災害的歷史案件，也沒有連結現場回報或 SOS 的共同案件 ID |
| `sos_reports` | 以 `msg_id` 為 ID 的一筆藍牙中繼 SOS 封包／求救紀錄 | ID 識別的是訊息，不是穩定的人員或救援案件；同一人多次發 SOS 可能形成多筆紀錄 |
| `earthquake_field_reports` | 一筆有時間、座標和 `observation` 的現場觀察 | 一筆觀察可能描述多人、建物或道路狀況，不能假設它就是一名受災者 |

目前地圖把 `emergency_reports` 和 `sos_reports` 分別列為案件來源，沒有將兩者連結或確認是否為同一個人；各來源上的狀態也是各自寫回資料列。新定義完成後，才有明確方式把「同一位受災者從 App 送出的救援摘要、藍牙 SOS 與他人回報」連到同一個 `RescueCase`，同時保留各筆來源紀錄。

這項決策定義的是後續系統的業務語意，**不是說目前 Firestore 中已經有個人案件表，或要立刻把舊資料全部搬成新格式**。舊資料要如何連結或遷移，應等資料模型與試辦流程確認後再設計。

### 地震事件分組和救援案件連結是兩件事

`earthquake_key` 用來回答「這筆現場回報屬於哪一次地震？」；`RescueCase` 用來回答「這是需要處理的哪一名受災者？」同一個 `DisasterEvent` 可以有許多 `FieldReport`、`RescueSite` 和 `RescueCase`。把回報分到同一場地震，**不代表這些回報描述的是同一個人或同一個案件**。

#### 目前地震回報實際如何分組

- 線上 `/api/earthquake/assess` 收到 CWA `EarthquakeNo` 和發震時間時，現在使用 `cwa:{EarthquakeNo}:{origin_time}` 作為 `earthquake_key`；使用者送出回報時，也會保存來源編號 `source_event_id`。若官方編號或發震時間缺漏，則回退到原本的欄位 hash。
- 救援端的事件選單以 `earthquake_key` 完全相同來分組；相同 key 的回報會一起計數並送去 AI 摘要。因此，**若多位使用者取得的線上地震欄位完全相同，這段程式會把他們的現場回報分到同一事件**。它不是以文字或座標相似度推斷。
- 若沒有 CWA 編號與發震時間，欄位 hash 仍可能因地點文字、時間格式、規模或震央座標差異而不同。CWA 編號與時間也只用於來源事件識別，不代表主震與餘震會自動併成同一救援行動。
- 模擬強震每次都生成新的 `time`；在本次程式調整前，這會讓每次測試變成不同事件。現在模擬回報統一使用 `test-simulation-earthquake-v1`，線上與離線流程都套用同一測試 key，因此重複模擬可以累積在同一個測試事件；地點文字仍標示「模擬強震（測試資料）」。

正式事件目前已優先使用 CWA `EarthquakeNo` 加發震時間形成來源 key；若來源沒有可用值，沿用欄位 hash。後續建立正式 `DisasterEvent` 資料模型時，仍建議另設內部不變的 `event_id`，把此來源 key 作為外部識別／別名，並補上人工合併不同來源事件的流程。

#### 目前 `emergency_reports` 不會自動合併進同一案件

目前沒有執行「將 `emergency_reports`、`sos_reports` 和 `earthquake_field_reports` 合併成同一筆救援案件」的功能：

- `emergency_reports` 以 `user_id` 為文件 ID；新摘要會更新該使用者的同一份文件，而且文件沒有 `earthquake_key`。
- `sos_reports` 以 `msg_id` 為文件 ID；它代表一次 SOS 訊息，不是穩定的受災者案件 ID。
- `earthquake_field_reports` 每筆是獨立觀察，雖有 `earthquake_key`，但目前沒有 `case_id` 或 `site_id` 關聯欄位。
- 地圖目前把一般救援摘要和 SOS 訊息分開列出；事件摘要只讀取指定 `earthquake_key` 的 `earthquake_field_reports`。

未來所說的「合併」應是建立一筆標準 `RescueCase`，再把確認屬於該人的來源紀錄連結過來；原始回報文件仍保留。例如同一人有一筆一般救援摘要、兩筆 SOS 和一筆旁人觀察，協調員核對後把四筆來源連到一個 `RescueCase`。同一個人只有在有足夠資訊確認時才連結；位置相近、姓名相同或文字類似只能提示協調員，不能自動當作同一人。若來源提到多名受災者，應先確認並分開連結，避免把不同人的傷勢資料混在一起。

**性質：** 後續資料模型與收件流程的實作規格；目前原型尚未建立這些關聯。

#### 地震事件識別碼

正式地震現在會優先使用 CWA `EarthquakeNo` 與發震時間組成 `cwa:{EarthquakeNo}:{origin_time}`，並把 `EarthquakeNo` 另存為 `source_event_id`。把發震時間納入 key 是為了防止不同報告重用編號時碰撞；CWA 資料預覽中可見相同 `EarthquakeNo` 出現在不同發震時間，因此不單獨把該欄位當唯一鍵。[CWA 小區域有感地震資料集](https://opendata.cwa.gov.tw/dataset/earthquake/E-A0016-002)。若缺少編號或時間，線上後端沿用欄位 hash；一般離線模式在沒有 CWA 識別資料時使用 `offline-...` key；模擬模式則使用固定測試 key。

`EarthquakeNo` 已從最新地震端點一路帶進評估與回報；CWA 地震列表去重也改為比較「編號 + 發震時間」，避免相同編號但不同發震時間的事件被誤刪。既有已儲存回報不會自動重算 key 或遷移；新的官方地震回報會開始使用上述來源 key。

建議採用下列相容策略，而不是直接把舊 key 換掉：

1. `DisasterEvent` 保存內部不變的 `event_id`，並可選保存 `source_provider = CWA`、`source_event_id = EarthquakeNo`。目前回報流程已保存來源編號，但尚未建立完整的 `DisasterEvent` 表／集合。
2. 新回報優先使用 CWA 編號與發震時間組成的來源 key；若尚未取得官方編號或時間，暫用本地 hash。
3. 把舊 `earthquake_key` 保存為事件別名／對照值，讓既有回報仍可查詢；若不同舊 key 後來確認是同一事件，由協調員合併事件別名，不改寫或刪除原始回報。
4. 離線回報保留離線產生的暫時識別碼與原始事件欄位；同步後由事件解析流程提出候選事件，不能只因時間接近就靜默改掛。

#### 收件、分流與連結規則

| 收到的來源 | 初始處理 | 協調員核實後的連結目標 |
|---|---|---|
| `earthquake_field_reports` 的觀察 | 保留原文與座標，依可用事件識別碼掛到 `DisasterEvent`；無法確認事件時進「待分流」 | 描述道路、建物或多人狀況時連到 `RescueSite`；明確描述某一人且核實後，才連到該人的 `RescueCase`；一筆來源可同時連事件、現場，也可經確認連一個或多個案件 |
| `emergency_reports` 的使用者救援摘要 | 保留目前使用者摘要及其 `user_id`；因目前沒有 `earthquake_key`，不以時間或座標自動指定地震事件 | 由本人求救或協調員核實後連到個人 `RescueCase`；若摘要實際描述多人，先建立現場分流，再逐人確認案件 |
| `sos_reports` 的 SOS 封包 | 每個 `msg_id` 保留為獨立訊息來源；`msg_id` 不等於人員 ID | 若有可核實的發送者／使用者關聯才連到個人案件；重複封包先標示候選重複，不能單憑訊息 ID 建立新受災者 |

資料關係建議獨立保存於來源文件之外，例如 `case_sources`／`report_links` 關聯集合，至少包含 `source_type`、`source_id`、`event_id`、可選 `site_id`／`case_id`、連結狀態、信心／理由、確認者及時間。原始來源文件照常保留；「合併」是新增或調整關聯，不是把不同來源文字覆寫成一筆，也不是刪掉重複來源。

#### 人工操作流程

1. 系統收件並保留原始來源，產生待分流項目；即時危險可先進高優先級佇列，不必等待 AI 摘要。
2. 系統提出可能的地震事件、現場或重複回報候選，顯示判斷依據；候選不自動等同確認。
3. 協調員選擇「連到既有事件／現場／案件」、「建立新事件／現場／個人案件」、「標記疑似重複」或「拆分多人描述」。
4. 每次連結、拆分、合併和撤銷都寫入操作歷程；可撤銷關聯但不刪原始來源。
5. AI 災情彙整以指定 `DisasterEvent` 的已連結觀察為輸入，摘要須顯示來源筆數、回報時間、位置範圍與未核實項目；AI 產物是可編輯草稿，核實與發布由協調員負責。

因此，正式資料現在優先以 CWA 編號加發震時間分組，缺少官方欄位時才用 hash；模擬資料共用固定測試 key。協調員現在可以把多個地震事件放入同一救援行動群組，但系統不會自動判定主震與餘震，也沒有把 `emergency_reports`、SOS 和現場觀察自動合成一個個人案件。舊 key 保持原狀，沒有遷移既有資料。

### 已實作：救援行動群組 MVP

救援端可建立一個 `rescue_incidents`（救援行動）文件，先放入一個地震事件，再把經協調員確認相關的其他事件加入 `event_keys`。同一行動的災情彙整會查詢這些事件 key 對應的第一手現場回報；原始回報文件不搬移、不覆寫。新增事件使用 Firestore `ArrayUnion`，重複加入同一 key 具冪等性。

救援端「災情彙整」頁提供建立行動、選取既有行動、加入目前選定地震，以及對整個行動產生 AI 摘要的入口。把餘震加入行動是協調員的明確操作；系統不依 48／72 小時自動判定餘震，也不把不同地震事件改成同一個 `earthquake_key`。

這是跨地震事件的檢視／摘要群組，**不是正式的個人 `RescueCase` 資料表，也不會把現場觀察自動連到一名受災者**。多人或地點型觀察仍應先核實，再由後續案件與來源關聯流程決定如何拆分及連結。群組目前只允許救援角色存取，尚未加入機關租戶隔離、行動結案操作或完整操作稽核。

### 已實作：現場、個人案件與來源關聯 MVP

- `rescue_sites` 代表一個待查證或已確認的地點；從回報建立時沿用該回報的位置與地震事件。
- `rescue_cases` 代表一名已知或匿名人士，初始狀態為 `待核實`，另存個案標示、情況摘要、優先級、座標、事件、可選現場及救援行動。
- `rescue_report_links` 以獨立關聯文件把原始 `earthquake_field_reports` 連到一個或多個現場／個人案件，記錄建立者、時間及連結說明。建立或連結不會覆寫或刪除原始觀察；同一回報可以連到一個現場及多名受災者。
- 救援端「現場回報」每筆資料可以建立現場、建立一名待核實個人案件，或連到同地震／同救援行動下的既有目標。跨不同地震的個案連結必須由協調員確認該來源事件和目標都屬於同一救援行動。

救援端新增「個人案件」工作區，可集中列出 `rescue_cases`，檢視匿名標示、狀態、優先級、座標、地震事件、已關聯現場及透過 `rescue_report_links` 找到的原始回報。從現場回報建立個人案件後會直接切換至工作區並選取新案件。介面以地點、規模、事件時間描述地震；模擬資料明確標成「模擬地震（測試資料）」並可顯示測試震央座標，內部 `earthquake_key` 不直接展示。任務地圖現在另顯示 50 公里內的 `rescue_cases` 個人案件，紫色標記與舊有救援摘要、藍牙 SOS 區分。個人案件工作區可按受限狀態流程更新案件，並在 `status_history` 保存前後狀態、操作者 ID 與時間；協調員可建立隊伍，外勤帳號透過隊伍邀請碼加入。案件進入「待派遣」後，協調員從隊伍名冊選擇受派隊伍並建立 `rescue_missions`；建立任務與案件轉為「已派遣」會在同一 Firestore 交易中完成。外勤帳號只能讀取所屬隊伍的任務，並可回報接受／拒絕、前往現場、抵達及任務結果。拒絕會將案件退回「待派遣」，前往現場更新為「救援中」，任務完成更新為「待確認結果」，仍需協調員確認是否已協助和結案。案件與任務都保存狀態操作紀錄。邀請碼目前可重複使用且無期限；結案後尚不能重開，組織租戶隔離及正式稽核治理仍未實作。多人觀察需由協調員逐人建立案件，不會自動按文字中的人數產生個案。

| 實體 | 用途 | 關係／重要欄位 |
|---|---|---|
| Organization | 機關、企業、校園或合作團體 | `organization_id`、名稱、服務區域、狀態 |
| Membership | 使用者與組織的任務關係 | `user_id`、`organization_id`、角色、隊伍、啟用狀態 |
| DisasterEvent | 一次地震或其他災害事件 | 外部事件識別碼、災種、發生時間、範圍、事件狀態 |
| RescueSite | 一個實際現場、地址或搜尋範圍 | `event_id`、座標／範圍、危害、估計人數、核實狀態 |
| FieldReport | 民眾或現場人員的原始觀察 | 原文、座標、觀察時間、來源、事件、現場／案件連結、回報狀態；原文保留 |
| RescueCase | 一名已知或匿名受災者的救援案件 | `event_id`、可選 `site_id`、優先級、位置、個案狀態、相關來源、負責機關 |
| RescueTeam | 可接收任務的一支救援隊 | 名稱、建立者、啟用狀態、外勤成員 |
| Mission | 指派給特定隊伍的工作 | `case_id` 或 `site_id`、`team_id`、指派者、任務狀態、開始／完成時間 |
| AuditEvent | 狀態及權限操作歷程 | 操作者、組織、時間、物件、前後值、理由 |

所有組織資料都應有明確的組織範圍；跨機關共用案件需經授權，而不是讓所有救援帳號自動看到所有資料。

## 5. 救援帳號與授權方式

### 原型／封閉試辦

可由專題管理者手動建立救援帳號，或使用單次、限時的邀請碼。若先沿用目前共用啟用碼，只應當作開發或受控試用的臨時機制，並在試辦結束後撤銷或輪替。

### 機關或企業正式導入

1. 建立組織租戶並指定該組織管理者。
2. 由組織管理者新增成員，或串接組織既有的單一登入身分系統。
3. 管理者依職務指派協調員、外勤人員、隊伍與服務區域。
4. 每次 API 請求同時檢查使用者身分、組織範圍、角色和案件／任務指派關係。
5. 人員離職、轉調或任務結束時，由組織管理者停用成員或撤回授權；狀態變更與權限異動留下稽核紀錄。

登入時選擇「協調員」或「外勤隊員」只是介面入口，不能作為授權依據。協調員帳號需使用管理者核發的啟用碼；外勤帳號需使用協調員建立隊伍時產生的邀請碼，後端會把帳號綁定到該隊伍，外勤任務 API 只回傳所屬隊伍任務。原型邀請碼目前可重複使用且未設期限，正式服務需補上撤銷、輪替、期限和使用紀錄。

## 6. 服務型式與導入路徑

建議先驗證一個合作場域，再決定商業形式：

1. **專題原型：** 使用合成資料演練「回報 → 核實 → 去重 → 排序 → 派遣 → 結案」流程。
2. **受控試辦：** 與一個校園、園區、民間防災團體或地方機關確認角色與事件流程，使用約定範圍的資料。
3. **組織服務：** 提供民眾端與組織工作台；依採用單位需求選擇代管雲端服務、專屬環境或機關自建方案，並提供帳號管理、訓練、維運及資料交換能力。
4. **擴大導入：** 完成租戶隔離、資安與個資治理、備援與離線方案、操作稽核、服務支援及合作系統整合後，再評估按組織授權或年度服務合約。

這是一個可驗證的產品假設，不代表已找到願意採購的客戶或完成正式系統要求。公部門雲端方案需按機關要求評估雲端服務與資安控制；政府機關有相關雲端服務資安參考指引。[數位發展部資安署：政府機關雲端服務說明](https://moda.gov.tw/ACS/laws/faq/28/744)

現場回報可能包含精確位置、身分線索、傷勢與健康資訊。正式試辦前應確認蒐集目的、必要欄位、可存取角色、保存期限、刪除／更正流程及服務提供者責任；個人資料與醫療健康資料適用的要求，應由合作機關與專業人員確認。[《個人資料保護法》](https://law.moj.gov.tw/LawClass/LawAll.aspx?PCode=I0050021)

## 8. 目前原型的明確邊界

- 目前有一般使用者、協調員及外勤隊員角色和基本隊伍歸屬，但沒有機關租戶、隊伍管理員或職務層級的細緻權限。
- 救援端的現場回報查詢目前沒有組織／區域範圍限制；多機關共用前必須補上隔離。
- 任務可連結個人案件並指派至隊伍名冊；地圖尚未顯示任務分派狀態，亦未提供協調員改派、取消或外勤即時位置追蹤。
- 個人案件狀態只能依目前流程轉換，並會保存前後狀態、操作者 ID 與時間；尚未具備理由欄位、完整稽核介面、組織權限或不可覆寫的獨立稽核事件。
- AI 災情摘要是依來源回報即時產生的草稿；正式採用前仍需人員核實與資料治理。
